# SparkFun OTA releases

## Release flow

1. Change `relod_sparkfun_v8_0/VERSION` and write release notes. Use a canonical
   three-part number higher than every release already installed for this profile.
   The initial infrastructure branch retains `8.0.0`; do not publish it as an
   upgrade to existing v8 devices. Confirm the fleet inventory before choosing
   the first compatibility release number.
2. Open a PR. **Validate** runs Python release tests, C++ policy tests and the
   production `sparkfun_c6` build. It packages the application image, full source
   commit, board, profile, size and SHA-256. Debug, dirty, stale, merged-flash and
   oversized images are rejected. Merge after review and passing CI.
3. Run **Publish firmware candidate** from `main`, selecting `main` or an existing
   `vMAJOR.MINOR.PATCH` tag whose commit is on main, and enter release notes (up to
   1024 characters). This builds once, stores its
   GitHub artifact, and uploads those exact bytes to private S3. It changes no
   device channel. A version cannot be reused for different bytes or commits.
4. Download that workflow's `candidate-<commit>` artifact. Test its `firmware.bin`
   over USB on the matching SparkFun hardware. Record its manifest SHA, device,
   mounting/calibration profile, results and reviewer. Do not rebuild for testing.
5. Register the pilot device in the server-owned S3 registry as `channel: test`.
   Run **Promote or pause firmware**, channel `test`, with the manifest key, current
   pointer ETag (including quotes), or `absent` if none exists, and an evidence
   summary/link (maximum 1024 characters). Test OTA on a second device running the
   preceding protocol-2 firmware version. The USB device already has this version
   and will correctly receive no update.
6. After the pilot passes, run the same workflow for `stable`. This verifies the
   stored bytes again and requires the exact artifact to be enabled in `test`.
   Approve the production environment deployment. No rebuild happens on promotion.

Production is **SparkFun ESP32-C6 Thing Plus**, environment `sparkfun_c6`, profile
`relod-6514-v1`. This profile describes the currently checked-in RELOD-6514 lid
calibration and wiring. Other mounts require calibration review and a separately
supported profile; do not register them under this profile just to deliver an
update. XIAO is not part of this release pipeline.

## One-time infrastructure

`infra/ota/roles.json` is generated by `python infra/ota/generate_template.py`.
It creates GitHub OIDC trust, separate candidate/test/production roles, and a
read-only API managed policy. It targets the existing `relod-firmware-updates`
bucket in `us-east-2`, account `734846754275`. It does not change that bucket's
private-access, encryption or versioning settings. No role can delete objects;
candidate writes require `If-None-Match: *`; pointer updates require an explicit
condition. Roles cannot register devices or update the anonymous legacy pointer.
The candidate and promoter roles can list this bucket to distinguish absent
objects from denied reads. They can read/write only their assigned object paths.

```sh
aws cloudformation deploy --template-file infra/ota/roles.json \
  --stack-name relod-ota-release-roles --capabilities CAPABILITY_IAM \
  --region us-east-2 --no-fail-on-empty-changeset
aws cloudformation describe-stacks --stack-name relod-ota-release-roles \
  --region us-east-2 --query 'Stacks[0].Outputs'
```

This template owns the account's GitHub OIDC provider. If one already exists
outside this stack, import/reuse it before deployment; do not create a duplicate.

Configure GitHub environments restricted to **branch `main` only**, with no tag
deployment rule. Workflow source must come from main even when the selected
firmware source is a release tag. Environment variables:

| Environment | Variable | Stack output |
| --- | --- | --- |
| `firmware-candidates` | `FIRMWARE_PUBLISH_ROLE_ARN` | `CandidateRoleArn` |
| `firmware-test` | `FIRMWARE_PROMOTE_ROLE_ARN` | `TestRoleArn` |
| `firmware-production` | `FIRMWARE_PROMOTE_ROLE_ARN` | `ProductionRoleArn` |

Require a hardware-owner reviewer for production. Verify your GitHub plan allows
that protection on this repository. If it does not, leave the production role
variable unset until an equivalent approval control is agreed. No permanent AWS
access keys belong in GitHub. Use an admin identity only for bootstrap; never put
root credentials in CI or Fly.

Deploy the companion `relod-api` selector with a dedicated identity attached to
`ApiReadPolicyArn`. Fly requires its own runtime credential provisioning; GitHub
OIDC credentials do not authenticate a running Fly Machine. Store a dedicated
read-only identity's credentials in Fly secrets, rotate them, and never print or
commit them. Start with:

```text
FIRMWARE_S3_BUCKET=relod-firmware-updates
AWS_REGION=us-east-2
FIRMWARE_S3_PREFIX=firmware
FIRMWARE_ROLLOUT_ENABLED=false
FIRMWARE_LEGACY_ROLLOUT_ENABLED=false
```

Enable the first gate only when the pilot is registered and test selection has
been verified. Keep legacy disabled. The Cloudflare website-read Worker is not
the S3 selector; devices continue to use `https://relod.fly.dev/latest_firmware`.
Keep the Worker's independent legacy rollout gate disabled.

## Device registry and stored objects

An administrator writes `firmware/devices/<12-lowercase-hex-MAC>.json`:

```json
{"schema_version":1,"enabled":true,"board":"sparkfun_esp32c6_thing_plus","hardware_profile":"relod-6514-v1","channel":"test"}
```

Use `stable` only for production-approved devices. MAC identity routes a device;
it is not an authentication secret. Devices cannot select their own channel.
Unknown, disabled, malformed or mismatched devices receive an empty URL. Missing
S3 objects, denied reads and invalid metadata also produce no offer.

Objects use these paths beneath `firmware/`:

- `releases/<board>/<profile>/<version>/<commit>/firmware.bin` and `manifest.json`
- `versions/<board>/<profile>/<version>.json`: immutable version claim
- `channels/<board>/<profile>/test.json` or `stable.json`: conditional pointers
- `audits/<board>/<profile>/<channel>/<promotion-id>.json`: immutable update intent

The manifest is published last, after checking stored bytes. An audit records
intent before the pointer write; it is **not** proof that promotion succeeded.
Confirm the pointer's `promotion_id` after a failed or interrupted command.
S3 versioning retains pointer history. A stale ETag fails rather than replacing
another operator's update; inspect the current pointer before retrying.

All test/stable promotion and pause workflows share one concurrency group. Use
that workflow as the operator path. Direct CLI calls do not provide a transaction
across the test and stable pointers: never run them concurrently with each other
or a workflow. If an emergency pause is queued behind a run awaiting approval,
cancel that pending run or disable the universal Fly gate immediately. GitHub
concurrency is not a FIFO queue; confirm the latest requested operation ran.

## Migration of deployed v8 devices

Old v8 requests are anonymous. They cannot be selectively targeted by the new
registry. Start by USB-flashing pilot devices with protocol 2; verify connectivity,
certificate validation and hardware behavior before considering a fleet update.
Anonymous legacy rollout has its own `legacy.json` pointer and an additional gate.
The ordinary workflows cannot change it. A separate reviewed migration must prove
the candidate matches **all** anonymous devices that may receive it. Leave it
disabled if hardware/profile inventory is uncertain. Do not use the test channel
as an anonymous fallback.

Protocol 2 checks at boot and when due on a measured or scheduled reporting wake.
It reserves the next check 24 hours ahead before Wi-Fi, so network failures do not
retry on every motion. A scheduled reporting wake can check even if the lid/range
sensor or measurement POST fails. Charger-only and motion-cooldown wakes remain
quiet. Battery must be readable, at least 30%, and at least 3.65 V. Cold resets
reset the retained deadline and can allow another check. Clock failure defers
OTA; it never disables TLS validation. Streaming has a 120-second overall and
5-second no-progress limit, in addition to connection/metadata/reporting time.

## Hardware acceptance record

Before stable, save a record with manifest SHA/commit/version, tester, device IDs,
board/profile, prior version, power source and results for:

- USB install of the exact artifact, startup identity and normal sensor/display,
  charging, lid and deep-sleep behavior.
- Trusted metadata/S3 TLS, correct clock, and rejection of an untrusted certificate.
- OTA from the preceding version, reboot, reported firmware version and SHA.
- Unknown device, wrong board/profile, paused channel, same/older version,
  expired URL, wrong size/hash and interrupted download: no activation.
- Poor Wi-Fi, low battery, failed measurements and failed uploads: bounded checks
  and expected sleep/retry behavior.
- At least one scheduled reporting wake with unavailable measurement data, and
  a full day of pilot operation to observe the retained OTA deadline.

CI does not prove hardware behavior. Automatic boot rollback and secure-boot
signature enforcement are not certified by this work. Retain USB recovery access.

## Pause, recovery and monitoring

To pause a channel, run **Promote or pause firmware** with `pause=true`, its current
manifest and current ETag. Pausing retains the version high watermark and works
even if the artifact is missing: it uses the current pointer without requiring
artifact downloads. A previous
version cannot be promoted over it; recovery is a higher-version tested build or
USB recovery. Pausing prevents future installs, not installs already downloaded.
For an emergency stop of all offers, set `FIRMWARE_ROLLOUT_ENABLED=false` on Fly.

The release owner checks the pilot immediately after install, after a scheduled
report and through the first 24 hours. Compare serial boot version/identity and
existing `firmware_version` measurement telemetry. Check normal ingest, sleep,
battery and reboot behavior against the hardware record. Unexpected reboot loops,
wrong-profile offers or a confirmed sensor/power regression require pausing and
investigation. Missing telemetry alone needs diagnosis because devices can sleep
or lack Wi-Fi. Never log presigned URLs or AWS secrets.
